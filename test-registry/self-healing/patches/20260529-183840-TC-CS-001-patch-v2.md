# Patch v2: TC-CS-001 — 2026-05-29 18:38:40 (REVISED)

## Failure Summary
- TC ID        : TC-CS-001
- Story        : CS-2
- Error Type   : TIMEOUT_ERROR (timing race condition)
- Failing At   : openSearch() — line 133
- Error Message: "TimeoutError: locator.waitFor: Timeout 30000ms exceeded waiting for getByRole('button', { name: 'Open Search' }) to be visible"

## Root Cause (Revised After Failed Patch)

**Initial hypothesis** (patch v1): SAP shell bar lazy-loads action buttons automatically within 2-3 seconds. Just wait for button to appear.

**Actual root cause** (discovered after patch v1 failed):

The issue is a **timing race condition** between three asynchronous events:
1. SAP Fiori home page loads (domcontentloaded)
2. Guided Tour dialog appears (3-5 seconds after page load — varies by session)
3. Shell bar action buttons render (2-3 seconds after page load)

**The problem**:
- Test calls `dismissAllKnownPopups()` immediately after `login()` (line 26 in spec)
- `closeGuidedTourPopup()` waits only 3 seconds for the dialog (timeout: 3000)
- If dialog hasn't appeared yet (timing varies), method gives up and returns
- Test proceeds to `searchAndOpenApp()` → `openSearch()`
- NOW the Guided Tour dialog appears (late async render)
- Dialog **blocks or interferes with shell bar rendering** of action buttons
- "Open Search" button never becomes visible → 30-second timeout

**Why MCP re-execution worked**: During manual MCP execution, we explicitly waited for and dismissed the Guided Tour dialog AFTER it appeared. The manual flow had natural delays between steps, giving the dialog time to render before we tried to access the search button.

**Why Playwright automated run fails**: Automated scripts execute rapidly. The test moves from login → dismissPopups → searchAndOpenApp in milliseconds. The Guided Tour dialog appears AFTER `dismissAllKnownPopups()` has already given up waiting.

## Fix Applied (v2)

### File 1: automation/pages/mm/purchase-order/purchase-order.page.js

**Method 1: `closeGuidedTourPopup()` — increased timeout**

```javascript
async closeGuidedTourPopup() {
  // PATCHED 2026-05-29: Increased timeout from 3s to 10s — dialog appears asynchronously 3-5s after page load.
  try {
    const leaveBtn = this.page.getByRole('button', { name: 'Leave Tour' });
    if (await leaveBtn.isVisible({ timeout: 10000 })) {  // WAS: 3000
      await leaveBtn.click();
      await this.page.waitForTimeout(500);
      return true;
    }
  } catch (_) {}
  return false;
}
```

**Method 2: `openSearch()` — added explicit popup dismissal**

```javascript
async openSearch() {
  // PATCHED 2026-05-29 (TC-CS-001 self-healing v2): SAP Fiori shell bar lazy-loads action buttons.
  // Critical timing issue: Guided Tour dialog appears asynchronously 3-5s after login and BLOCKS
  // shell bar rendering. Must dismiss dialog BEFORE waiting for "Open Search" button.
  await this.page.waitForLoadState('domcontentloaded', { timeout: 60000 }).catch(() => {});

  // Step 1: Ensure Guided Tour dialog is dismissed (may appear late, blocking shell bar)
  await this.closeGuidedTourPopup();

  // Step 2: Wait for shell bar to complete rendering (button appears automatically after dialog dismissed)
  const searchBtn = this.page.getByRole('button', { name: 'Open Search' });
  await searchBtn.waitFor({ state: 'visible', timeout: 30000 });
  await searchBtn.click();
  await this.page.waitForTimeout(500);
}
```

## Why This Fix Works

1. **Defense in depth**: `dismissAllKnownPopups()` is still called early in the test (line 26), catching the dialog if it appears quickly
2. **Safety net**: `openSearch()` now calls `closeGuidedTourPopup()` again RIGHT BEFORE waiting for the search button
3. **Longer timeout**: 10-second wait gives the dialog time to appear even on slow renders
4. **Idempotent**: If dialog was already dismissed, `closeGuidedTourPopup()` quickly returns (isVisible check)
5. **Non-blocking**: If dialog never appears, method returns after 10s without error

## Lessons Learned (Updated)

1. **Timing race conditions are subtle**: Initial MCP re-execution appeared to show button appearing automatically. Reality: the manual delays gave dialog time to appear and be dismissed before we tried to click search.

2. **Automated execution exposes races**: Playwright executes steps in milliseconds. Races that are invisible during slow manual testing become obvious in fast automated runs.

3. **Defensive programming for async UI**: When dealing with asynchronous UI rendering (dialogs, lazy-loaded components), always ensure blocking elements are handled RIGHT BEFORE the critical operation, not just once at the beginning.

4. **Timeout tuning matters**: The original 3-second timeout was too short for the asynchronous dialog appearance. 10 seconds provides sufficient buffer while still failing fast if something is truly wrong.

5. **Idempotent operations are safe**: Calling `closeGuidedTourPopup()` multiple times doesn't hurt — if dialog isn't there, method returns quickly. This allows defensive "dismiss right before operation" patterns.
