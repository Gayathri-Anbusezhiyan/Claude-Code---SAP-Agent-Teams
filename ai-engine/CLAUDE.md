# SAP S/4HANA Cloud Automation Project

This project automates SAP S/4HANA Cloud scenarios using Playwright, following a Page Object Model (POM) pattern with automated execution and detailed reporting.

## Project Structure

```
test-registry/                         → All generated artifacts and test outputs
  ├── jira/                      → Jira Agent output
  │   ├── userstories/           → Fetched user stories (.md + .json per issue)
  │   │   └── {KEY}/strategy/    → Test strategy artefacts per story
  │   ├── epics/                 → Fetched epics (.md + .json per issue)
  │   └── index.json             → Master registry of all fetched issues
  ├── testcases/
  │   └── AI-generated testcases/ → Test cases generated by the TestCase Agent (.md + coverage matrix + summary JSON)
  ├── testdata/                  → Parameterized test datasets (.json) + placeholder guides (.md)
  ├── automation/                → Playwright automation framework
  │   ├── tests/                 → Playwright test specs (.spec.js) - one per SAP module
  │   ├── pages/                 → Page Object Model files (POM pattern)
  │   ├── fixtures/              → Test data and page fixtures
  │   ├── helpers/               → Utility functions (login, error recovery, etc.)
  │   ├── config/                → Playwright configuration
  │   ├── test-data/             → Resolved test data JSON files
  │   └── test-results/          → Playwright execution results (traces, screenshots, videos, HTML reports)
  ├── exploration-data/          → MCP exploration captures (snapshots, selectors, execution records)
  │   ├── execution/             → Per-TC execution records ({KEY}/{TC-ID}/)
  │   ├── selectors/             → Aggregated selector maps per module-app
  │   └── snapshots/             → Legacy per-app snapshots
  ├── scriptless-results/        → Scriptless execution results
  ├── self-healing/              → Self-Healing Agent outputs
  │   ├── failures/              → Failure analysis reports
  │   ├── re-executions/         → Scriptless re-execution records
  │   └── patches/               → Applied patch records
  ├── defects/                   → Defect Logging Agent outputs
  │   └── {KEY}/                 → Classification + defect records per story
  └── reports/                   → PDF/Excel test execution reports

ai-engine/                       → All AI agent infrastructure
  ├── agents/                    → Agent Teams (one folder per agent phase)
  │   ├── jira-agent/            → Phase 1: Fetch Jira issues (active)
  │   ├── test-strategy-agent/   → Phase 2a: Analyse stories + define test strategy (active)
  │   ├── testcase-agent/        → Phase 2b: Generate test cases (active)
  │   ├── automation-agent/      → Phase 3+4: Explore SAP via MCP + generate scripts (active)
  │   ├── self-healing-agent/    → Phase 5: Analyze failures, re-execute, patch scripts (active)
  │   └── defect-logging-agent/  → Phase 6: Classify failures + log Jira defects (active)
  ├── prompts/                   → Generation prompt templates (.md)
  ├── blueprints/                → POM automation blueprints
  ├── utils/                     → Utility scripts (Excel export, PDF generation)
  ├── architecture/              → Architecture documentation
  ├── playwright-report/         → Playwright HTML reports (legacy)
  ├── .mcp.json                  → MCP server configuration
  └── CLAUDE.md                  → Master documentation

Root configuration files:
├── .env                         → Environment variables (SAP credentials, Jira config)
├── .gitignore                   → Git ignore rules
├── .vscode/                     → VSCode workspace settings (hides node_modules, .playwright-mcp)
├── .claude/                     → Claude Code configuration and slash commands (required at root)
├── .playwright-mcp/             → Playwright MCP server cache (required at root, hidden in IDE)
├── package.json                 → NPM dependencies and scripts
├── package-lock.json            → NPM dependency lock file
└── node_modules/                → NPM dependencies (hidden in IDE)
```

## Agent Teams

This project uses an Agent Teams architecture where each agent handles one phase of the pipeline:

```
Jira Agent   →  Test Strategy  →  TestCase Agent  →  Automation Agent  →  Self-Healing  →  Defect Logging
(Phase 1)       (Phase 2a+2b)     (Phase 2c)        (Phase 3+4)          (Phase 5)         (Phase 6)
fetch issues    analyse+strategy  generate TCs      explore+generate     heal failures     log defects
└── test-registry/jira/  └── strategy/  └── test-registry/testcases/  └── test-registry/exploration-data/  └── test-registry/self-healing/  └── test-registry/defects/
                                  └── test-registry/testdata/   └── test-registry/automation/
```

Agents live in `ai-engine/agents/`. Each agent has `agent.md` (capabilities), `skills/` (task instructions), and `config/` (env-based configuration).

### Automation Agent (Phase 3+4 — Active)

Executes SAP test cases via Playwright MCP to capture real element refs and behaviors (Phase 3), then generates 100% executable Playwright scripts (Phase 4).

#### Slash Commands

| Command | What It Does |
|---------|--------------|
| `/run-scriptless {KEY\|TC-ID}` | Execute TCs via Playwright MCP, verify each step's expected result, report PASS/FAIL (no scripts needed) |

#### Output Structure
```
test-registry/exploration-data/execution/{KEY}/
├── {TC-ID}/
```

### Self-Healing Agent (Phase 5 — Active)

Analyzes Playwright test runner failures, re-executes failing TCs via MCP to find what works, and patches scripts. Escalates to Defect Logging Agent when SAP itself is broken.
See `ai-engine/agents/self-healing-agent/agent.md` for full documentation.

#### Slash Command

| Command | What It Does |
|---------|--------------|
| `/self-heal {TC-ID}` | Analyze failure → re-execute via MCP → patch scripts. Escalates to `/log-defect` if SAP is broken |

#### Decision Logic
```
/run-tests fails
  └─ /self-heal {TC-ID}
       ├─ SAP works in MCP → patch scripts → re-run to verify
       └─ SAP also fails  → /log-defect {TC-ID}
```

#### Output Structure
```
test-registry/self-healing/failures/{timestamp}-{TC-ID}-failure.json      ← Error type + failing locator + recommendation
test-registry/self-healing/re-executions/{timestamp}-{TC-ID}/             ← MCP re-execution: tried strategies, what worked
test-registry/self-healing/patches/{timestamp}-{TC-ID}-patch.md           ← What changed + verification command
```

### "Generate testcases from requirements"

When you say **"Generate testcases from requirements"**, follow these steps:

1. **Read all requirement files** from the `requirements/` folder
   - Each file describes SAP module capabilities (MM, SD, FI, HR, etc.)

2. **Read the prompt template** at `prompts/requirements-to-testcase-generation.md`
   - This defines test case structure, guidelines, and quality checks

3. **For each requirement file**, generate corresponding test case markdown with structure:

   ```
   ## Test Case ID: TC_[MODULE]_[SCENARIO]_[###]
   **Module:** [SAP Module - MM/SD/FI/HR]
   **Scenario:** [Business Scenario Name]
   **Description:** [What this scenario validates]
   **Priority:** [High/Medium/Low]
   **Test Type:** [Functional/Integration/Security/Performance]

   ### Business Objective
   [Business reason for this scenario]

   ### Preconditions
   - [User role/authorization required]
   - [Master data prerequisites]
   - [System state requirements]

   ### Test Steps
   | Step | Action | Expected Result |
   |------|--------|-----------------|
   | 1 | [Navigate to transaction] | [Page loads] |
   | 2 | [Enter data] | [Fields populated] |

   ### Expected Result
   - [Expected system state after execution]
   - [Required database changes]
   - [Confirmation messages expected]

   ### Error Scenarios
   - [Edge case 1 and expected error]
   - [Validation error and expected message]

   ### Status
   [To be filled during execution]

   ### Notes
   [Module-specific considerations, dependencies]
   ```

4. **Test Case ID Convention:**
   - `TC_MM_PO_###` — Materials Management - Purchase Order
   - `TC_MM_GR_###` — Materials Management - Goods Receipt
   - `TC_SD_SO_###` — Sales & Distribution - Sales Order
   - `TC_SD_DN_###` — Sales & Distribution - Delivery Note
   - `TC_FI_###` — Financial Accounting
   - `TC_HR_###` — Human Resources
   - (Expand as needed for other modules)

5. **Coverage rules** — For each capability in the requirement file, generate:
   - **Happy path** — Normal successful execution
   - **Alternative path** — Valid alternate scenarios (different user roles, different transaction types)
   - **Error path** — Invalid inputs, authorization failures, validation errors (if mentioned)

6. **Priority assignment:**
   - **High** — Core transactional processes (PO creation, SO fulfillment, payment posting)
   - **Medium** — Standard operations, reporting scenarios
   - **Low** — Edge cases, master data maintenance

7. **Save output** to `test-registry/testcases/` folder:
   - Name by module and scenario (e.g., `test-registry/testcases/mm-purchase-order-testcases.md`)
   - Include date of generation in notes

8. **Quality checks before finishing:**
   - Every capability has at least one test case
   - All SAP-specific terminology is accurate
   - Preconditions match actual SAP requirements (authorization objects, master data)
   - Expected results reference actual SAP messages/document numbers
   - Test cases follow SAP transaction sequences
   - Test case IDs are sequential and unique within module
   - No system-specific URLs or credentials in test steps

### "Generate automation scripts from testcases"

When you say **"Generate automation scripts from testcases"**, follow this 2-phase approach:

---

#### **Phase 1: Exploratory Scriptless Execution (Data Capture)**

Execute one round of each test case scriptlessly to capture real-world SAP data:

1. **Execute each test case** using the scriptless workflow (MCP browser tools)
2. **Capture exploration data:**
   - **Element References (refs)** from `browser_snapshot` output — accurate SAP locators
   - **SAP page states** — Transaction codes executed, page titles, screen sequences
   - **Element interactions** — Which buttons/fields exist, their states, visibility
   - **Timing requirements** — SAP page load times, batch processing waits
   - **SAP messages** — Success messages, error codes, validation messages
3. **Capture error scenarios:**
   - **Authorization errors** — SAP authorization failure messages
   - **Validation errors** — Field validation messages from SAP
   - **Business logic errors** — SAP business rule violation messages
   - **Timeout issues** — Long-running SAP operations (posting, approval workflows)
   - **Missing elements** — Fields/buttons unavailable in certain SAP configurations
4. **Document findings** in JSON format:
   ```json
   {
     "feature": "mm-purchase-order",
     "testCases": [
       {
         "id": "TC_MM_PO_001",
         "capturedData": {
           "transactionCode": "ME21N",
           "pageTitle": "Create Purchase Order",
           "locators": {
             "vendorField": { "ref": "e23", "strategy": "name", "value": "LIFNR" },
             "materialField": { "ref": "e30", "strategy": "name", "value": "MATNR" },
             "saveButton": { "ref": "e32", "strategy": "role", "value": "button", "name": "Save" }
           },
           "pageLoadTime": "3-4 seconds",
           "successMessage": "Purchase Order",
           "successMessageRef": "e50",
           "issues": []
         }
       }
     ]
   }
   ```

---

#### **Phase 2: Generate Scripts from Captured Data**

Use the captured exploration data to generate robust automation scripts:

1. **Read the test case files** from `test-registry/testcases/` folder
2. **Read the POM blueprints** from `ai-engine/blueprints/` folder
3. **Read captured exploration data** from Phase 1
4. **For each test case module**, generate or update:
   - **Locators** (`test-registry/automation/pages/<module>/<module>.locators.js`) — Use captured refs and strategies
   - **Page Object** (`test-registry/automation/pages/<module>/<module>.page.js`) — Action methods with SAP timeouts
   - **Test spec** (`test-registry/automation/tests/<module>.spec.js`) — Playwright test cases with SAP assertions
   - **Helpers** (`test-registry/automation/helpers/<module>.helper.js`) — SAP-specific utilities (approval workflows, etc.)
5. **Script generation rules:**
   - Each test case `test(...)` block title must include the TC ID (e.g., `TC_MM_PO_001`)
   - Use captured element refs from Phase 1
   - Use captured page load times for `waitForLoadState` and explicit waits
   - Use exact SAP message text from Phase 1 for assertions
   - Handle SAP authorization/validation errors documented in Phase 1
   - Use `domcontentloaded` for waitForLoadState (SAP uses dynamic rendering)
   - All timeouts based on observed SAP demo server performance from Phase 1
   - Include SAP transaction code navigation (e.g., `/nME21N` to start transaction)

- **Play buttons** appear next to each `test(...)` block in `.spec.js` files — click to run that test
- **Test Explorer** (`Ctrl+Shift+;`) shows all tests organized by SAP module — run any test or group
- **Headed mode** is enabled by default locally (browser visible). In CI, tests run headless.
- If the extension doesn't detect the config, add to `.vscode/settings.json`:
  ```json
  {
    "playwright.config": "test-registry/automation/config/playwright.config.js"
  }
  ```

### HTML Reports

Each test execution generates a **timestamped HTML report** that auto-opens in the browser.

**What the report contains:**
- **Test case level** — Pass/fail status for every test case (TC_MM_PO_001, TC_SD_SO_002, etc.)
- **Action step level** — Expand any test case to see the full Playwright trace with every SAP interaction (navigate, click, fill, assert) as individual steps with before/after screenshots
- **Traces** — Recorded for every test. Click "Trace" in the report to open the Trace Viewer with a timeline of all SAP interactions, DOM snapshots, network calls, and console logs
- **Screenshots** — Captured at every action step, showing SAP UI state
- **Videos** — Full video recording of each test execution against SAP

**Report location:**
```
test-registry/automation/test-results/reports/<timestamp>/
├── index.html          ← Main HTML report (auto-opens)
├── results.json        ← JSON results for programmatic access
└── junit.xml           ← JUnit XML for CI/CD integration
```

**View a past report:**
```bash
npx playwright show-report test-registry/automation/test-results/reports/<timestamp>
```

### PDF Test Reports

Generate professional PDF reports with test execution summary and test steps in tabular format:

```bash
# After running tests, generate PDF from results.json
npm run report:pdf test-registry/automation/test-results/reports/<timestamp>/results.json

# Example with specific timestamp
npm run report:pdf test-registry/automation/test-results/reports/2026-08-22T14-30-15/results.json
```

**PDF Report includes:**
- ✅ Executive summary (total tests, passed/failed counts, pass rate)
- ✅ Individual test case details with status badges
- ✅ Test steps in tabular format (Step | Action | Expected Result)
- ✅ Failure error messages for failed tests
- ✅ Execution duration and timestamps
- ✅ Professional SAP-branded styling

**Output:** PDF saved in same folder as `results.json` or custom path:
```bash
npm run report:pdf <results.json> test-registry/pdf-reports/my-report.pdf
```

## Key Patterns & Conventions

### SAP Module Codes
- **MM** — Materials Management (PO, GR, IR, Inventory)
- **SD** — Sales & Distribution (Sales Order, Delivery, Billing)
- **FI** — Financial Accounting (AP, AR, GL, Cost Center)
- **HR** — Human Resources (Payroll, Recruitment, Leave)
- **PM** — Plant Maintenance

### Test Case Naming

**Agent-generated (Jira stories):** `TC-{PROJECT}-{NNN}`
- Examples: `TC-CS-001`, `TC-CS-002`, `TC-CS-003`
- Sequential counter across all test cases for a given story (no module or type in the ID)

**Legacy (requirements-based):** `TC_[MODULE]_[SCENARIO]_[###]`
- Examples: `TC_MM_PO_001`, `TC_SD_SO_003`, `TC_FI_AP_002`

### Page Object Organization
- One POM per SAP module/transaction family
- Locators in `.locators.js` (exported as constants)
- Actions in `.page.js` (methods that perform user operations)
- Module helpers for SAP-specific workflows

### Error Recovery
- All error scenarios from scriptless execution must become coded logic
- Use `sap-ui5-helper.js` for SAP-specific DOM interactions
- Implement retry logic for transient SAP errors

|--------------|-------|---------|
| `/jira-fetch-userstories` | Jira Agent | Fetch all Stories → `test-registry/jira/userstories/` |
| `/jira-fetch-epics` | Jira Agent | Fetch all Epics → `test-registry/jira/epics/` |

| `/define-test-strategy {KEY}` | Test Strategy Architect | Define strategy → strategy.md |
| `/generate-testcases {KEY}` | TestCase Agent | Generate full TC suite → `test-registry/testcases/AI-generated testcases/` + `test-registry/testdata/` |
| `/testcase-pipeline {KEY}` | Test Strategy Architect + TestCase Agent | Run all 3 phases in one go: analyse → strategy → test cases |
| `/v1-pipeline` | E2E Pipeline Agent | **Phases 1–4**: Jira import → TestCase pipeline → Scriptless explore → Generate scripts |
| `/v1-pipeline {KEY}` | E2E Pipeline Agent | Same Phases 1–4 for a single story key |
| `/e2e-pipeline` | E2E Pipeline Agent | **Full 7-phase run**: Phases 1–4 + run tests + self-healing + defect logging |
| `/e2e-pipeline {KEY}` | E2E Pipeline Agent | Same full 7-phase pipeline for a single story key |
| `/run-scriptless {KEY\|TC-ID}` | Automation Agent | Execute TCs via Playwright MCP (no scripts needed), verify each step's expected result, report PASS/FAIL → `test-registry/scriptless-results/{KEY}/` |
| `/automate {KEY}` | Automation Agent | **Phase 1**: execute all TCs via MCP, capture real locators + behaviors. **Phase 2**: generate locators.js + page.js + fixtures.js + spec.js + data.json |
| `/run-tests {KEY\|module\|TC-ID}` | Playwright Runner | Execute scripts via `npx playwright test`, display structured pass/fail summary with recommended next steps |

| `/self-heal {TC-ID}` | Self-Healing Agent | Analyze failure → re-execute via MCP to find what works → patch scripts. Escalates to `/log-defect` if SAP is broken |
| `/log-defect {TC-ID}` | Defect Logging Agent | Classify failure vs ACs → if app defect: create Jira Bug linked to parent story + add story comment |
